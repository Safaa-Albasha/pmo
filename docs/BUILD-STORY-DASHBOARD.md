# قصة بناء لوحة المتابعة (Dashboard)

هذه قصة بناء لوحة متابعة PMO خطوة بخطوة: ما الذي قررناه، ولماذا، وكيف تحققنا. كل رقم هنا من المستودع نفسه أو من تشغيل الاختبارات.

## 1. نقطة البداية

كان عندنا محرّك (Engine) مكتوب بـNode.js بدون أي مكتبات خارجية، يحسب القيمة المكتسبة (EVM) والمسار الحرج (CPM) ومؤشرات الرشيق (Agile) والمخاطر، ويقرأ كل شيء من ملفات JSON داخل مجلد `.pmo/`. وكان عندنا تقرير HTML تفاعلي يُولَّد كملف واحد.

السؤال كان: كيف يرى مدير المشروع حالة المشروع **مباشرة** على جهازه، وتتحدّث الصفحة وحدها عندما يكتب الوكلاء (Agents) في الملفات؟

## 2. القرار الأول: بدون مكتبات

- لا React ولا Express ولا مكتبات رسوم ولا CDN.
- الخادم: وحدة `http` المدمجة في Node.
- الصفحة: ملف HTML واحد وملف CSS وملف JS عادي.
- الرسوم البيانية: SVG مرسوم يدويًا بنفس طريقة التقرير الموجود.

**لماذا؟**
1. المستخدم يشغّلها على جهازه، وأحيانًا على Windows داخل شبكة شركة. كل مكتبة إضافية = `npm install` إضافي ومشكلة محتملة.
2. لا اتصال بالإنترنت = لا تسريب لبيانات المشروع.
3. أقل كود = أقل أماكن للأخطاء الأمنية.

النتيجة: `package.json` ما زال بلا أي dependencies.

## 3. القرار الثاني: الأرقام من المحرّك فقط

الصفحة لا تحسب أي مؤشر. الخادم يستدعي نفس الدالة التي يستخدمها التقرير (`buildReportData`)، وهي بدورها تستدعي دوال الحالة وEVM وCPM والرشيق والمخاطر نفسها التي يستدعيها الـCLI.

وأثبتنا ذلك باختبار: نشغّل

```bash
node engine/cli.js status --dir examples/waterfall/.pmo
```

ونقارن النتيجة بما يرجعه `/api/state`. يجب أن تكون متطابقة حرفيًا (مثلًا CPI = 0.9302 وتاريخ الانتهاء المتوقع 2026-06-23 في مثال المستودع).

## 4. الصفحات

المشروع، الجدول الزمني (Gantt)، الـBacklog والسبرنتات، المخاطر مع الخريطة الحرارية، القضايا، التغييرات، الجودة، أصحاب المصلحة، الدروس المستفادة، الوكلاء الأحد عشر، الموافقات والقرارات، ومستكشف الملفات.

صفحة الوكلاء لا تحتوي نصًا مكتوبًا يدويًا عن كل وكيل؛ الخادم يقرأ ملفات `agents/*.md` ويستخرج منها المهارات والملفات وما هو تلقائي وما يحتاج موافقة. فإذا تغيّر ملف وكيل، تتغيّر الصفحة.

## 5. التحديث المباشر

الخادم يحسب «بصمة» لمجلد `.pmo/` كل ثانية (أسماء الملفات وأحجامها وأوقات تعديلها). إذا تغيّرت، يرسل حدثًا للصفحة عبر Server-Sent Events، فتعيد الصفحة تحميل البيانات. لا WebSocket ولا مكتبة.

## 6. الأمان في النسخة الأولى (قراءة فقط)

- يستمع على `127.0.0.1` فقط.
- يفحص ترويسة `Host` (حماية من DNS rebinding).
- يقبل `GET` فقط؛ أي `POST` أو `PUT` أو `DELETE` يرجع `405`.
- مستكشف الملفات لا يعرض إلا ملفات داخل مجلد المشروع: يرفض `../` والمسارات المطلقة وروابط symlink التي تخرج من المجلد.
- Content-Security-Policy يمنع أي سكربت خارجي.
- النصوص تُبنى كعُقد نصية، لا `innerHTML`.

## 7. السؤال الذي غيّر النسخة: «هل هناك طريقة يقدر يعدّل عليها؟»

نعم، لكن بشرط ألا نكسر بروتوكول الموافقات. البروتوكول يقسم السجلات إلى:

- **سجلات حرة** (القضايا، الدروس، الـBacklog): تُكتب مباشرة ثم يُتحقق منها.
- **سجلات محمية** (المخاطر، الجدول، الميزانية، التغييرات…): لا تتغيّر إلا عبر اقتراح يوافق عليه مدير المشروع.

فقررنا:

1. **وضع التعديل اختياري:** `--edit`. بدونه تبقى اللوحة للقراءة فقط كما كانت.
2. **الصفحة لا تكتب ملفات ولا ترسل مسارات.** ترسل نوع النموذج والحقول فقط، مثل `{"kind":"risk.add","data":{...}}`. ملف جديد في المحرّك (`engine/edit.js`) هو الذي يقرر أي ملف، ويفحص الحقول، ويقرر: حفظ مباشر أم اقتراح.
3. **الحفظ المباشر** يمر بنفس دوال المحرّك: `execute` ثم `validate` ثم الكتابة.
4. **الاقتراح** يمر بـ`propose` نفسها التي يستخدمها الوكلاء، فيظهر في `approvals.json` وفي `/pmo:approvals` أيضًا.
5. **الموافقة والرفض** من صفحة الموافقات تستدعي `apply` نفسها، فيُكتب القرار في `decisions.json`.
6. **زر «تعديل» على الاقتراح** يعمل كما يعمل في مهارة `/pmo:approvals`: اقتراح جديد مصحّح، ثم رفض الأصلي بملاحظة `superseded by APR-…`.
7. **سجل تدقيق:** كل خطوة تُضاف إلى `audit.json` باسم `PM via dashboard` مع الوقت وقيمة «قبل/بعد». أضفنا هذا الملف إلى قائمة السجلات المحمية حتى لا يعدّله وكيل يدويًا.

قرار متعمَّد: أصحاب المصلحة سجل حر في البروتوكول، لكن من اللوحة جعلناه **اقتراحًا**، لأن المطلوب كان أن يمر عبر الموافقة.

## 8. الأمان في وضع التعديل

كل طلب كتابة يمر بهذه الفحوص بالترتيب، وأي فشل يوقفه قبل لمس أي ملف:

| الفحص | عند الفشل |
|---|---|
| الطلب موجّه إلى `localhost` أو `127.0.0.1` (Host) | 403 |
| الطلب جاء من نفس الجهاز | 403 |
| الطلب جاء من صفحة اللوحة نفسها (`Origin` و`Sec-Fetch-Site`) | 403 |
| رمز الجلسة صحيح (`X-PMO-Token`) | 401 |
| المحتوى JSON (`Content-Type: application/json`) | 415 |
| الحجم لا يتجاوز 64 KB | 413 |
| JSON صالح، والحقول معروفة وقيمها صحيحة | 400 |
| العنصر موجود | 404 |
| الاقتراح ما زال معلّقًا وبياناته لم تتغيّر | 409 |

رمز الجلسة عشوائي (24 بايت) يُنشأ عند كل تشغيل ويُطبع في الـTerminal داخل رابط: `http://localhost:4173/#token=…`. الرمز في جزء `#` من الرابط، فلا يصل إلى الخادم في الطلب العادي ولا يُسجَّل. الصفحة تحفظه في `sessionStorage` (يختفي بإغلاق التبويب) ثم تحذفه من شريط العنوان. والرمز لا يظهر أبدًا في `/api/state`.

لماذا كل هذا والخادم محلي؟ لأن أي موقع تفتحه في نفس المتصفح يستطيع أن يحاول إرسال طلب إلى `localhost`. فحص الأصل والرمز ونوع المحتوى معًا يمنع ذلك (CSRF).

## 9. الواجهة

- شارة حمراء «وضع التعديل» في الأعلى، وشريط يشرح ما يُحفظ فورًا وما يحتاج موافقة.
- النماذج تفتح في درج جانبي (Drawer)، بالعربية والإنجليزية.
- كل نموذج يقول بوضوح: «سجل حر — يُحفظ الآن» أو «سجل محمي — يحتاج موافقتك».
- قبل الإرسال شاشة تأكيد تعرض القيم (وفي التعديل: القيمة قبل ← بعد).
- أخطاء الحقول تظهر تحت الحقل نفسه، بنفس رموز الأخطاء التي يرجعها المحرّك.
- بعد النجاح: رسالة قصيرة، والصفحة تعيد تحميل الأرقام من المحرّك.

## 10. Windows

جرّب صفاء اللوحة على Windows من فرع `main` فظهر: `npm error Missing script: "dashboard"`. السبب ببساطة أن اللوحة ما زالت في الفرع `claude/pmo-dashboard`. أضفنا تنبيهًا واضحًا في الـREADME:

```bat
git fetch origin
git checkout claude/pmo-dashboard
npm run dashboard -- --dir examples\waterfall\.pmo --edit
```

وفي PowerShell، إذا ضاعت المعاملات بعد `--`:

```powershell
node engine\dashboard.js --dir examples\waterfall\.pmo --edit
```

وفي الكود:
- المسار يُحل بـ`path.resolve`، فالمسارات بالشرطة `\` أو `/` أو بحرف القرص (`D:\…`) كلها تعمل.
- فحص «هل الملف داخل مجلد المشروع» صار بـ`path.relative` بدل مقارنة نصوص، واختبرناه بقواعد Windows عبر `path.win32` حتى على Linux.
- مسار مثل `scope\backlog.json` يُعامَل مثل `scope/backlog.json`.

## 11. الاختبارات

الأمر:

```bash
npm test
```

- قبل وضع التعديل: **85** اختبارًا ناجحًا، منها 7 للوحة.
- بعده: **95** اختبارًا ناجحًا، 0 فشل (10 اختبارات جديدة في `tests/dashboard-edit.test.js`).

ما تغطيه الاختبارات الجديدة:
- بدون `--edit`: كل كتابة ترجع 405 والملفات لا تتغيّر (نقارن لقطة لكل الملفات قبل وبعد).
- مع `--edit`: بدون رمز ← 401، من موقع آخر ← 403، بدون Origin ← 403، نص عادي بدل JSON ← 415، طلب أكبر من 64 KB ← 413، JSON مكسور ← 400.
- 12 حمولة غير صالحة (احتمال 9، تاريخ 30 فبراير، حقل غير معروف مثل `file: "../../etc/passwd"`…) كلها 400 ولا يتغيّر أي ملف.
- خطر جديد ← اقتراح `APR-0001` بالمعرّف `R6`، وملف `risks.json` لا يتغيّر حتى الموافقة؛ بعد الموافقة يظهر R6 في نتائج `cli.js risk` والمشروع يبقى صالحًا، والقرار في `decisions.json`.
- الموافقة مرتين ← 409. الرفض قبل التطبيق = تراجع: R7 لا يصل إلى الملف.
- القضايا والدروس وحالة الـBacklog تُحفظ مباشرة؛ نسبة إنجاز النشاط تبقى اقتراحًا.
- زر التعديل: اقتراح جديد ورفض الأصلي `superseded by APR-0002`، وتعديل اقتراح وكيل لا يسمح بتغيير الملف المستهدف.
- محاولات الخروج من المجلد (`..\secret.txt`، `C:\Windows\win.ini`، `\\server\share`) ← 404.
- مسارات Windows بـ`path.win32`.

وفوق الاختبارات، شغّلنا الصفحة فعليًا في Chromium بمقاسين (1440 و390 بكسل) بالعربية، وأكملنا المسار كاملًا: اقتراح خطر، خطأ في حقل، تأكيد، موافقة، تعديل قضية، تحديث إنجاز نشاط، درس جديد، طلب تغيير، وتعديل اقتراح. لم تظهر أخطاء في الـConsole غير ردود 400 المقصودة في اختبار الحقل الخاطئ.

## 12. ما لم نفعله (عن قصد)

- لا حذف لأي سجل من اللوحة (البروتوكول يمنع الحذف).
- لا `baseline` ولا نشر مستندات من اللوحة؛ هذه الاقتراحات تُوافَق أو تُرفض فقط.
- لا تسجيل دخول ولا مستخدمين متعددين: اللوحة لمدير مشروع واحد على جهازه.
- لا «تراجع» تلقائي لتعديلات السجلات الحرة؛ القيمة السابقة محفوظة في `audit.json`.
